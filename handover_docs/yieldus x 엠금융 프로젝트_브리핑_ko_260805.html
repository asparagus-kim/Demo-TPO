1우리가 만들려던 것

한 문장

점주가 사업자등록번호 10자리만 입력하면, 그 매장에 어울리는 음악이 재생됩니다. 그 외에 아무것도 묻지 않습니다.

왜 음악인가

소상공인은 금융 상품으로 접근하기 어려운 고객군입니다. 그래서 점주가 실제로 원하는 것을 먼저 제공하고, 그 대화에서 상담 데이터를 만들어 파트너사인 엠금융에 전달하는 구조입니다.

음악은 훅(hook)이고, 사업은 금융 상담입니다. 이 순서를 뒤집어 이해하면 이후 모든 우선순위 판단이 어긋납니다.

이 데모의 두 가지 용도

대상용도
대표자 · 엠금융본개발에 투자하기 전, 실제 데이터로 개념이 성립함을 증명
D2D 영업 담당점주 앞에서 폰을 열어 번호를 넣고 음악을 들려주는 세일즈 키트

두 용도 모두 같은 요구를 만듭니다 — 실제로 돌아가는 서비스처럼 보여야 합니다. 그래서 결과를 미리 계산해 두지 않았고, 분석에 실제로 2~10초가 걸립니다.

범위 밖

검토했지만 제외한 것들입니다. 다시 꺼내지 마십시오 — AI 음악 생성, 상담 신청 폼과 CRM 연동, 관리자 콘솔, 다국어 UI, 회원 가입, 결제.

2여기까지 온 과정

시간 순서입니다. 각 전환에는 이유가 있고, 그 이유를 모르면 되돌리려 하게 됩니다.

출발점 — 이전 개발자의 구현

사업자번호를 넣으면 매장의 분위기를 에너지 · 템포 · 무드 세 숫자로 산출하는 FastAPI 백엔드가 있었습니다. 국세청 상태조회, 상권 매칭, Google Places, 기상청, LLM 리뷰 분석까지 파이프라인이 갖춰져 있었습니다.

중요한 전제

당시 유료 API 예산이 승인되지 않았습니다. 그래서 사업자번호 → 상호명 조회를 민간 API(머니핀) 화면을 크롤링해 임시 구현했습니다. 잘못된 선택이 아니라, 예산 제로라는 제약에 대한 첫 번째 답이었고 실제로 데모가 돌았습니다.

전환 ① 크롤링 → 공식 API

크롤링은 대상 페이지가 바뀌면 깨지고, 컨테이너에 헤드리스 브라우저가 필요하고, 팔려는 제품에 넣기엔 법적으로 불편합니다. bizno 공식 REST API로 교체했습니다.

다만 예산 제약은 그대로입니다. 비공식 경로를 공식 경로로 바꿨을 뿐, 가격은 여전히 0원입니다. 그리고 bizno 무료 플랜은 상호명만 줍니다.

기존 방식은 주소에서 동 이름을 뽑아 전국 행정동 엑셀에서 찾는 것이었습니다. 30곳 벤치마크에서 정확도 37%였습니다.

전환 ⑤ 음원 추천 기능 신규 개발

이전 버전은 E/T/M 숫자를 산출하고 끝났습니다. 데모가 차트로 끝났습니다. 제품의 약속이 음악인데 음악이 나오지 않으면 증명이 안 됩니다. 추천 엔진을 새로 만들었습니다.

전환 ⑥ 2업종 → 11업종

파일럿 대상은 엠금융과 협의해 카페 · 피트니스로 확정했습니다. 그래서 음원 매니페스트도 2업종만 담았습니다. 스코프 결정이었지 누락이 아닙니다.

확장 계기: 미용실을 넣어보니 업종군을 못 찾아 카페 재즈가 1위로 나왔습니다. 그런데 원본 라이브러리에는 미용실 75곡, 바 173곡, 서점 105곡이 이미 있었습니다. 664곡 중 604곡을 안 쓰고 있었습니다. 병목은 라이브러리가 아니라 매니페스트였고, 넓히는 데 드는 비용은 큐레이션 시간뿐이라 확장성을 택했습니다.

3특이사항 — 반드시 알아야 할 5가지

① 무료 API 구성은 목표가 아니라 유예된 상태입니다

원래 지향점은 유료 API로 상호명 · 주소 · 업종을 한 번에 받는 것이었습니다. 예산 미승인으로 미뤄진 것뿐입니다.

유료 전환은 개선 항목이 아니라 원래 계획의 복귀입니다. 예산 승인만 남았고, 전환 시 약 280줄의 코드와 화면 하나가 통째로 사라집니다.

② 후보 선택 화면은 버그가 아닙니다

실제 사업자 10곳으로 측정한 결과, 5곳은 자동 확정, 5곳은 사용자 선택이 필요했습니다.

피트니스월드는 중구와 종로구에 이름이 완전히 동일한 매장이 있고 사업자도 다릅니다. 두 후보의 점수가 1.00 : 1.00입니다. 어떤 알고리즘도 이름만으로 구분할 수 없습니다. 주소만이 답입니다.

약국 · 편의점 · 병원처럼 흔한 상호가 많은 업종에서는 이 화면이 더 자주 뜹니다.

③ 현재 UI는 임의로 작성한 값입니다

레이아웃, 색상, 문구, 정보 배치 모두 전체 디자인 변경 예정입니다. 확정 사양이 아니므로 보존하려 애쓰지 마십시오.

대신 유지해야 할 것은 화면이 아니라 API 응답 스키마와 상태 분기입니다 — 정상 / 후보 선택 필요 / 오류, 이 세 가지를 새 UI도 반드시 처리해야 합니다.

④ 리뷰는 매장당 5건이 상한입니다 — 돈으로 못 늘립니다

Google Places API 자체의 제약이라 유료 플랜으로도 늘어나지 않습니다. 그런데 리뷰 텍스트가 분위기 점수의 50%를 차지합니다. 근거가 얇다는 뜻이고, 현재 설계의 가장 큰 품질 리스크입니다. (논의 ②에서 다룹니다.)

⑤ 음원 메타데이터는 스프레드시트에서 관리합니다

곡의 분위기 정보 — BPM, 에너지, 무드, 적합 업종, 적합 시간대 등 — 는 사내 Google 스프레드시트에서 관리하고, 아래 경로로 서비스에 반영됩니다.

Google 스프레드시트 음원 메타데이터 원본 (사람이 관리) │ 내보내기 ▼ data.js 664곡 · 플레이어 프로젝트의 정본 │ scripts/curate_demo_tracks.py ▼ data/demo_tracks.json 620곡 · 이 서비스가 읽는 매니페스트 │ ▼ 런타임 매칭 외부 호출 없음

매칭에 실제로 쓰는 필드: bpm · energy_level · valence · arousal · suitable_industries · suitable_time_slots · customer_density_fit · purpose_tags · genre · mood · vocal_type

제외한 필드: warmth · sophistication · quality_score(채워진 곡이 극소수) / suitable_weather(전곡 동일값이라 변별력 없음)

매니페스트가 메타데이터를 자체 포함하므로, 런타임에는 스프레드시트나 플레이어 프로젝트 폴더를 참조하지 않습니다. 곡을 추가하거나 메타데이터를 고친 뒤에는 큐레이션 스크립트를 다시 돌려 매니페스트를 갱신합니다.

6논의 ① 음원 매칭 정확도를 어떻게 높일 것인가

현재 방식과 그 한계를 먼저 공유하고, 제가 생각한 방향을 제안합니다. 더 나은 안이 있으면 그쪽으로 가는 것이 좋습니다.

지금 어떻게 고르고 있나

매장의 E/T/M 점수를 목표값으로 두고, 후보 곡들과의 거리를 계산해 가까운 순으로 10곡을 뽑습니다. 가중치는 에너지 30% · 템포 25% · 무드 20% · 시간대 15% · 혼잡도 10%입니다.

핵심 설계 — 풀 내 상대 정규화

곡 메타데이터와 매장 점수는 스케일이 호환되지 않습니다.

valence 0.65~0.85 로 폭이 좁음 → 절대 비교하면 무드가 사실상 무시됨 energy_level 피트니스 곡은 대부분 8.0 → 상수라 어떤 절대 기준으로도 구분 불가 bpm 카페 60~129 / 헬스 118~160 → 분포가 거의 겹치지 않음

그래서 각 축을 후보 풀 안에서 최소–최대 정규화하고 목표값의 상대 위치와 비교합니다. 폭이 좁은 축도 변별력을 되찾고, 값이 일정한 축은 자동으로 "정보 없음"이 되어 점수에서 빠집니다.

측정된 한계 3가지

한계 1 — 피트니스 업종 내부에서 구분이 거의 안 됩니다

헬스장 62곡이 대부분 energy_level 8의 EDM입니다. 목표 에너지를 60에서 75로 올려도 상위 10곡 중 8곡이 그대로입니다.

즉 "붐비는 24시 헬스장"과 "조용한 동네 헬스장"이 거의 같은 플레이리스트를 받습니다. 카페는 284곡으로 늘어 인접 구간 겹침이 3~5/10로 개선됐습니다.

원인은 알고리즘이 아니라 음원 메타데이터입니다.

한계 2 — 시간대 태그가 부족합니다

원본 664곡 중 lunch 태그가 붙은 곡이 104곡뿐입니다. 일부 업종군은 점심 시간대 곡이 아예 없어, 곡을 더 넣어도 해결되지 않습니다.

한계 3 — 전곡 청취 검사는 아직 이루어지지 않았습니다

620곡 전체를 대상으로 한 청취 검사는 아직 진행 전입니다. 알고리즘이 정확해도 곡 자체가 매장 BGM으로 맞지 않으면 효과가 반감되므로, 업종별 표본부터 순차적으로 확인해 나가는 것이 좋겠습니다. 참고로 가사가 있는 곡이 191곡입니다.

7논의 ② 매장 정보 분석 정확도를 어떻게 높일 것인가

정확도가 걸리는 지점은 셋입니다

지점 1 — 매장 특정 (가장 큰 문제)

주소가 없어 이름만으로 찾습니다. 10곳 중 5곳이 사용자 선택을 거쳤습니다. 약국 · 편의점처럼 흔한 상호 업종에서는 더 심해집니다.

해결책은 명확합니다 — 유료 API 도입. 알고리즘으로는 한계가 있습니다. 이름이 완전히 같은 두 매장을 이름으로 구분할 방법은 없습니다.

도입 전까지의 완화책으로 논의할 만한 것: 점주에게 지역만 물어보기 (시/군/구 한 단어). 후보를 크게 줄일 수 있고, 사업자번호보다 입력 부담이 작습니다.

지점 2 — 분위기 판단의 근거가 얇습니다

리뷰 5건이 점수의 50%를 담당합니다. 리뷰가 아예 없는 매장도 있습니다 (실측: 피트니스월드 0건).

현재 웹 검색 보강은 리뷰가 없을 때만 작동하는 폴백입니다. 이를 상시 보강으로 바꾸면 근거가 두꺼워집니다. 다만 웹 검색 품질이 들쭉날쭉해 어떤 신뢰도 기준으로 섞을지가 논의 대상입니다.

추가로 검토할 만한 것: 네이버 플레이스 리뷰(한국 소상공인 리뷰가 훨씬 많음), 인스타그램 해시태그, 배달앱 리뷰.

지점 3 — 상권 판정 (해결됨, 다만 검증 세트가 작음)

37% → 90%로 올렸습니다. 다만 벤치마크가 30곳이고 기대 레이블은 제 판단입니다. 상권 분류에 객관적 정답이 없다는 점을 감안해야 합니다.

지방 · 비수도권에서 같은 임계값이 통하는지는 검증되지 않았습니다. 현재 벤치마크는 서울 중심입니다.
